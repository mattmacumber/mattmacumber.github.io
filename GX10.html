This is the CUDA companion to the original Framework Desktop guide: Building a Private AI Server.

Introduction

This is the NVIDIA/ARM companion to "Building a Private AI Server". Same goals, same OS philosophy, same inference focus — different silicon.

After my writeup on the Framework desktop, I was given access to an ASUS Ascent GX10, featuring NVIDIA's GB10 Grace Blackwell GPU with 128 GB of coherent unified LPDDR5x. It can run DeepSeek V4 Flash using antirez's DS4 inference engine (CUDA build) and exposes an OpenAI-compatible API to local development tools.

While the Framework is ROCm and x86-64, the GX10 is CUDA on aarch64. This makes the software stack significantly differnt, but I'm keeping the same "understandable and maintainable" goal.

Street price for the GX10 starts around $2,999 (1 TB) before tax. For better or worse, storage is soldered in place. There are no aftermarket options, no real reason to open the case.

Chapter 1 - Why Build a Private AI Server?

I've spent nearly thirty years writing software, sometimes professionally. During the past year I've gone from dismissing LLMs as unreliable code generators to using them daily for research, code generation, debugging, documentation, and automation. The productivity gains for me are real, but consuming these models through cloud APIs has some problems for me:

  • Usage-based pricing
  • Internet dependency
  • Vendor lock-in
  • Privacy concerns
  • Hidden prompts and changing model behavior
  • Quotas

Local inference removes most of those problems with some obvious downsides:

  • Fixed Capabilities
  • Higher upfront cost
  • Limited compute capacity
  • Responsibility for maintaining the software stack

This is also a learning experience for me. I'm not really concerned with all dimensions of efficiency.

Glossary of Terms

  • AMD - Company that designs and sells CPUs and GPUs
  • ROCm - AMD's software stack for data processing built around HIP
  • HIP - C++ API and kernel language for AMD GPUs
  • Strix Halo - The code name for the AMD Ryzen AI Max+ chips
  • NVIDIA - A company that designs and sells GPUs (and now Grace CPU + Blackwell GPU packages)
  • CUDA - NVIDIA's proprietary API for general-purpose GPU computing
  • GB10 - NVIDIA Grace Blackwell superchip: 20-core Arm CPU + Blackwell GPU, coherent unified memory
  • GX10 - ASUS Ascent GX10: compact desktop AI box built on GB10 (same class as DGX Spark)
  • SBSA - Server Base System Architecture; the aarch64 Linux ABI used by CUDA toolkit runfiles for Grace
  • Vulkan - A cross-platform GPU API. Like OpenGL, but newer
  • Metal - Like Vulkan, but Apple-only
  • x86-64 - The current Intel/AMD 64 bit instruction set
  • aarch64 - The name for 64 bit ARM instruction set

Chapter 2 - Design Goals

  • Runs (at least) one large model extremely well
  • Runs whatever linux distro I want
  • Minimal overhead
  • Upstream software whenever practical
  • Reproducible
  • Easy upgrades
  • Easy recovery
  • Avoid vendor-specific software (skip DGX OS / NGC appliance layers where possible)
  • Minimize black boxes

My ideal upgrade process looks like this:

ssh server
cd software
git pull
make
systemctl restart software

Here's what I'm not considering: safety, security, local privacy.

The end product will be open to anyone on your lan, documents and responses will be sent without encryption.

This is only a "how to get it working" guide. There are a lot of other concerns that should cater to your particular needs and environment.

The Framework Desktop is covered in the companion guide. This document is the GX10 path.

Why the ASUS Ascent GX10

The two machines are very similar at a high level.

GB10 Grace Blackwell — 20-core Arm (10× Cortex-X925 + 10× Cortex-A725) plus an integrated Blackwell GPU with 5th-gen Tensor Cores and FP4. Up to ~1 PFLOP of AI performance (vendor FP4 rating).

128 GB LPDDR5x coherent unified memory — Same magic number as the Framework build. Enough headroom for DeepSeek V4 Flash (~81 GB asymmetric quant) plus KV cache and OS. NVLink-C2C between Grace and Blackwell means no PCIe hop for tensors.

Memory bandwidth — Up to 273 GB/s. Roughly double the Strix Halo peak bidirectional figure (~123 GB/s). Prefill-heavy workloads should benefit.

CUDA — The mature inference and tooling ecosystem. DS4, llama.cpp, and most research code assume CUDA first.

Form factor — 150 × 150 × 51 mm, ~240 W PD adapter. Smaller than the framework.

Tradeoffs — aarch64-only (no casual x86 binary reuse), proprietary NVIDIA stack, fixed storage, and Gentoo on arm64 + NVIDIA isn't "supported" by anyone.

Why 128 GB Matters

Running local models is a game of memory ceilings:

Model Size Example Fits in 128 GB? Fits in 32 GB? Fits in 16 GB?
7B (Q4) Llama 3 8B ✓ ✓ ✓
14B (Q4) Qwen 2.5 14B ✓ ✗ / tight ✗
32B (Q8) Qwen 3 32B ✓ ✗ ✗
70B (Q4) Llama 2 70B ✓ ✗ ✗
90+ GB MoE (2/8 bit) DeepSeek V4 Flash Yes ✗ ✗

128 GB is the threshold where full-size frontier-class models become feasible on a single consumer-priced machine. Below that, you're limited to distilled or heavily quantized models.

If one box isn't enough, GB10 platforms are designed to cluster over ConnectX-7 (e.g. two GX10s for larger MoE footprints). That's a future experiment, if someone want to lend me another one.

Better alternatives than following this guide

  • If you only run 7B models: use a discrete GPU on a PC you already own.
  • If you need many concurrent users: multiple discrete GPUs (or a real server) is simpler.
  • If you just want a chat bot: find a small model that runs on hardware you already have.
  • If you want x86 + open GPU stack: follow the Framework / Strix Halo guide instead.
  • If you want the vendor path with least pain: install NVIDIA DGX OS and live in their container/tooling world.

Chapter 4 - A Bit About Unified Memory

This is the architectural feature that makes the entire project possible. Consider how data is copied in a traditional discrete GPU setup.

Traditional Discrete GPU Setup

The memory on the GPU is fast, but limited (e.g. 24 GB). For a modest sized model, every inference step can require shuttling data over the PCIe bus. Model weights, KV cache, and intermediate activations all compete for the same VRAM. Maintaining performance with larger models requires multiple GPUs.

Unified Memory (Grace + Blackwell)

On GB10, the Grace CPU and Blackwell GPU share a coherent LPDDR5x pool joined by NVLink-C2C. The GPU can address system memory without a classic PCIe copy for every tensor:

  • A ~90 GB model fits without splitting or streaming
  • KV cache lives alongside model weights without VRAM starvation
  • No PCIe transfer overhead for attention traffic
  • Programming model is CUDA on a coherent address space (still NVIDIA-shaped, not HSA)

The bandwidth tradeoff vs discrete cards still exists: flagship GDDR/HBM GPUs can exceed 1,000 GB/s unidirectional. GB10 peaks around 273 GB/s — lower than discrete flagships, higher than Strix Halo's ~123 GB/s bidirectional peak. For prompt processing (parallel, bandwidth-limited), discrete GPUs still win on raw throughput. For large-context generation where capacity matters, unified memory wins by letting the model fit at all.

Chapter 5 - Storage

Understanding the workload - Why Random IOPS Matter

Flash storage is usually graded by sequential write speed. A fast NVMe drive can hit 7500 MB/s. Modern high-context LLM engines can treat disk as a dynamic cache tier, continuously reading and writing KV history states during long sessions. For the software I'm interested in, the KV persistence layer is limited by random IO. Sequential throughput is nice when loading models, but the runtime limitation is random read/writes.

What you get on the GX10

ASUS ships fixed-capacity NVMe (1, 2 or 4 TB). It is noticably slower than the Samsung SSD I chose for the Framework.

In this install the internal drive showed up as:

Disk /dev/nvme0n1: 1.82 TiB
Disk model: ESL02TBTLCZ-27J2-TYN

Factory GPT layout (kept as-is):

/dev/nvme0n1p1   298M EFI System
/dev/nvme0n1p2   1.8T Linux filesystem

No dedicated swap partition in this layout. With 128 GB RAM and a headless inference box, hopefully there's no need. We can also create a "swapfile" if that turns out to be beneficial.

Filesystem: Why XFS

When all cores are processing inference or concurrent agent scripts, filesystem metadata contention can become a real bottleneck. Under heavy parallel metadata workloads, XFS generally scales better than ext4. ZFS is excellent but RAM-hungry — that RAM should go to inference, not ARC.

Chapter 6 - BIOS / Firmware Notes

Disable the hardware watchdog

Do this first. Disable the watchdog timer. I was experiencing random reboot during long inferrence tasks. I though I had faulty hardware until I found it in the BIOS.

Other settings worth checking

  • Secure Boot — Disabled, Lets me boot the software I want, without having to ask permission.
  • Fast Boot — Disabled, makes it easier to catch the boot process.
  • Power resume — What to do in the event of a power failure.

Unlike Strix Halo, there is no "UMA framebuffer size" knob that lets you shift memory between "main" RAM and VRAM. Coherent unified memory on GB10 is handled by the NVIDIA stack, not an AMD UMA reservation.

A great OS doesn't do things you don't want. The choice depends on how much control you need and how much maintenance you're willing to accept.

Boot persistence — modules, dracut, device nodes

This is the tricky bit. There are slicker ways to handle this, but I kept running into the unkindness of NViDA software. We're just giving udev some explicit help.

sudo tee /etc/modules-load.d/nvidia.conf >/dev/null <<'EOF'
nvidia
nvidia-uvm
nvidia-modeset
nvidia-drm
EOF

sudo mkdir -p /etc/dracut.conf.d
sudo tee /etc/dracut.conf.d/nvidia.conf >/dev/null <<'EOF'
omit_drivers+=" nouveau nova_core "
install_items+=" /etc/modprobe.d/nvidia.conf "
EOF

sudo tee /usr/local/sbin/nvidia-create-devices.sh >/dev/null <<'EOF'
#!/bin/bash
set -euo pipefail
modprobe nvidia 2>/dev/null || true
modprobe nvidia-uvm 2>/dev/null || true
modprobe nvidia-modeset 2>/dev/null || true
modprobe nvidia-drm 2>/dev/null || true
/usr/bin/nvidia-modprobe -c 0 -u >/dev/null 2>&1 || true
major_nvidia=$(awk '$2=="nvidia"{print $1}' /proc/devices | head -n1)
major_ctl=$(awk '$2=="nvidiactl"{print $1}' /proc/devices | head -n1)
major_modeset=$(awk '$2=="nvidia-modeset"{print $1}' /proc/devices | head -n1)
major_uvm=$(awk '$2=="nvidia-uvm"{print $1}' /proc/devices | head -n1)
[[ -n "${major_ctl:-}" ]] || major_ctl="${major_nvidia:-}"
[[ -n "${major_modeset:-}" ]] || major_modeset="${major_nvidia:-}"
[[ -n "${major_nvidia:-}" && ! -e /dev/nvidia0 ]] && mknod -m 666 /dev/nvidia0 c "${major_nvidia}" 0
[[ -n "${major_ctl:-}" && ! -e /dev/nvidiactl ]] && mknod -m 666 /dev/nvidiactl c "${major_ctl}" 255
[[ -n "${major_modeset:-}" && ! -e /dev/nvidia-modeset ]] && mknod -m 666 /dev/nvidia-modeset c "${major_modeset}" 254
[[ -n "${major_uvm:-}" && ! -e /dev/nvidia-uvm ]] && mknod -m 666 /dev/nvidia-uvm c "${major_uvm}" 0
[[ -n "${major_uvm:-}" && ! -e /dev/nvidia-uvm-tools ]] && mknod -m 666 /dev/nvidia-uvm-tools c "${major_uvm}" 1
exit 0
EOF
sudo chmod 755 /usr/local/sbin/nvidia-create-devices.sh

sudo tee /etc/systemd/system/nvidia-devices.service >/dev/null <<'EOF'
[Unit]
Description=Create NVIDIA device nodes for GB10
After=systemd-modules-load.service
Before=nvidia-persistenced.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/nvidia-create-devices.sh

[Install]
WantedBy=multi-user.target
EOF

sudo mkdir -p /etc/systemd/system/nvidia-persistenced.service.d
sudo tee /etc/systemd/system/nvidia-persistenced.service.d/override.conf >/dev/null <<'EOF'
[Unit]
After=nvidia-devices.service systemd-modules-load.service
Requires=nvidia-devices.service
EOF

sudo tee /etc/udev/rules.d/70-nvidia.rules >/dev/null <<'EOF'
ACTION=="add", SUBSYSTEM=="pci", ATTR{vendor}=="0x10de", ATTR{class}=="0x030000", RUN+="/usr/local/sbin/nvidia-create-devices.sh"
KERNEL=="nvidia", RUN+="/usr/local/sbin/nvidia-create-devices.sh"
KERNEL=="nvidia_uvm", RUN+="/usr/local/sbin/nvidia-create-devices.sh"
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now nvidia-devices.service nvidia-persistenced.service
sudo dracut -f --kver "$(uname -r)"

Chapter 11 - DS4: The Inference Engine

Why DS4?

Same rationale as the Framework guide:

  • llama.cpp — excellent generalist; breadth over depth on any single architecture
  • vLLM — datacenter multi-user serving; overkill for a single-user headless box
  • LM Studio — great for exploration; more overhead for always-on serving
  • DS4 (DwarfStar 4) — optimized for DeepSeek V4's MLA, compressed KV, and MoE routing on 128 GB+ machines, including SSD-backed KV state

The Model

DeepSeek V4 Flash uses asymmetric quantization — dense attention / router / shared experts at 8-bit, MoE blocks at 2-bit — landing around ~81 GB. It fits in the 128 GB pool with headroom for KV, disk cache, and OS. Target a 128K context window and an OpenAI-compatible API.

KV cache sizing (same math as the AMD guide)

DeepSeek V4 MLA compresses KV to roughly ~14.5 KiB per token:

  • 128K context ≈ ~1.8 GB in memory
  • --kv-disk-space-mb 27648 ≈ ~15 warm 128K threads before eviction

Chapter 14 - Takeaways

Memory capacity still matters more than FLOPS

128 GB coherent unified memory is the feature that makes DeepSeek V4 Flash practical on a desk. The GX10 adds higher bandwidth and a CUDA-first software world compared with Strix Halo.

CUDA is the path of least resistance for models — not for Gentoo

Getting nvidia-smi healthy on arm64 Gentoo is the hard part (device nodes, nouveau blacklisting, SBSA toolkit, persistenced ordering). Past that, the app layer is all the same.

Two boxes, two stacks

Framework Desktop ASUS Ascent GX10
Arch x86-64 aarch64
GPU stack ROCm / HIP CUDA
Peak BW ~123 GB/s ~273 GB/s
OS friction AMD firmware + HSA knobs NVIDIA modules + device nodes
Repurposing Easy x86 general PC Not sure it is good for anything else

Chapter 15 - Troubleshooting

Hardware Issues

Watchdog-induced reboots

Symptom: Random reboots during compiles, driver loads, or long inference.

Cause: Hardware watchdog left enabled.

Fix: Disable watchdog in BIOS/firmware (Chapter 6). This was a day-one fix on this machine.

Secure Boot blocks custom kernel / drivers

Symptom: System refuses to boot Gentoo GRUB or NVIDIA modules fail policy checks.

Fix: Disable Secure Boot for this install path.

Install media Issues

Gentoo live ISO fails on GX10

Symptom: Native Gentoo live environment is unusable for partitioning / stage3.

Fix: Boot a NixOS ISO (or another known-good aarch64 live image) and proceed with the Gentoo chroot install from there.

NVIDIA Issues

nouveau owns the GPU

Symptom: nvidia module fails to bind; nvidia-smi missing devices.

Fix: Blacklist nouveau, rmmod nouveau, load nvidia / nvidia-uvm / nvidia-modeset / nvidia-drm, rebuild dracut with omit_drivers+=" nouveau nova_core ".

Missing /dev/nvidia* nodes

Symptom: Modules loaded but CUDA apps fail to open devices.

Fix: Run /usr/local/sbin/nvidia-create-devices.sh and enable nvidia-devices.service before nvidia-persistenced.

Portage _cfg0000_nvidia.conf surprise

Symptom: Custom modprobe options disappear after emerge.

Fix: Promote the _cfg* file to /etc/modprobe.d/nvidia.conf and re-add NVreg_RestrictProfilingToAdminUsers=0.

CUDA runfile tries to ship a driver

Symptom: Toolkit installer wants to replace kernel modules.

Fix: Use --toolkit only (as in Chapter 9). Keep drivers on Portage.

Kernel / boot Issues

Root not found / NVMe missing in initramfs

Symptom: Emergency shell on first boot.

Fix: dracut --force --kver … --add-drivers "nvme nvme_core" and verify root= UUID in GRUB_CMDLINE_LINUX.

DS4 / client Issues

Same as the Framework guide:

  • Context too small — raise --ctx / --ctx-max or shrink prefill chunks
  • KV cache miss tax — keep client maxTokens high enough for finish=stop
  • /tmp/ds4.lock permission denied — remove or fix permissions on the lock file
  • OpenClaw 128-token death loop — set maxTokens to 2048–4096
